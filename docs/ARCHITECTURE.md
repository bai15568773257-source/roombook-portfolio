# 設計とコードの読みどころ

この資料はコードから確認できる構造を説明します。性能や安全性の保証、本人の担当範囲の証明ではありません。

## 1. リクエストの流れ

`compose.yaml` で Web・API・DB のサービスを定義しています。ブラウザは Nginx の画面にアクセスし、`site/nginx.conf` の `/api/` 設定から FastAPI へ処理が渡ります。MariaDB のポートはホストに公開していません。

主なファイル：`compose.yaml`、`site/nginx.conf`、`site/app.js` の `api()`。

## 2. 予約の登録

`app/main.py` の `create_reservation()` は入力日時、営業時間、予約時間などを検証し、必要に応じて承認待ちにします。対象の会議室をロックしてから、既存予約との重複を調べます。DB には同一条件の予約に対する一意制約もあります。

画面上のチェックだけに依存しない構成です。ただし、重複防止の保証には独立 DB を使った同時実行テストが必要です。

## 3. 認証・管理権限

`get_current_user()` がセッションを確認し、`require_password_ready()` と `require_admin()` が後続 API の利用条件を確認します。パスワードは bcrypt によるハッシュとして保存する構成です。画面プレビューの仮データは `demo/` 内で完結し、本体の認証処理は変更していません。

## 4. 初期化と永続化

`init_database()` が空のデータベースにテーブル・会議室・最初の管理者を作成します。既存 DB ではスキーマ調整や管理者同期も走るため、デモ環境は既存業務 DB と分離します。

MariaDB の保存領域は Compose の named volume、報表は `reports/` です。これらのデータを原始コードのリポジトリに含める必要はありません。

## 5. 面接で説明する際の項目

- どの業務上の困りごとから、予約・承認の流れを決めたか。
- AI に何を依頼し、自分はどこを確認・修正したか。
- NAS / Docker の設定やトラブルに、どう対応したか。
- 実装済み機能と、まだ十分に検証できていない部分は何か。

実際に行った内容を記載し、コードから確認できる機能と本人の担当実績を区別します。
